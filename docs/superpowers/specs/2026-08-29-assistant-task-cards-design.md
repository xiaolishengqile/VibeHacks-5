# 个人助理任务卡片设计

## 目标

把工作日历从“待办标题列表”升级为“可执行的个人助理计划”：系统在生成排期时同时生成并保存任务详情，给出实际工作时段、执行步骤、交付标准、专业建议、风险和兜底方案；用户点击任意日历任务即可立即查看完整卡片。

## 产品原则

1. 任务详情在首次生成或重新排期时一次性生成并持久化，点击时不再请求模型。
2. 排期只能落在周一至周五的个人工作时段内，不安排周末和强制晚间加班。
3. 每日工作量不得填满整个工作日，沿用个人工作模型中的每日容量和安全缓冲，为临时事项、沟通和休息保留时间。
4. 建议必须针对工作类型。例如演示文稿类任务应建议先写叙事文稿、缺失数据先占位、预留预审和打磨时间。
5. 每项工作至少有一个可观察的风险触发条件和对应兜底动作，不能只写空泛提醒。
6. 旧项目和手动待办没有智能详情时仍可打开，由本地规则提供基础说明。

## 非目标

- 第一版不提供卡片内富文本编辑；用户通过重新安排指令修改计划。
- 第一版不在点击卡片时再次调用模型。
- 第一版不新增日历拖拽改期、通知推送或多人协同系统。
- 第一版不引入新的界面或数据处理依赖。

## 数据模型

新增结构化任务详情：

```ts
interface WorkContingency {
	readonly risk: string;
	readonly trigger: string;
	readonly action: string;
}

interface WorkNodeDetail {
	readonly summary: string;
	readonly steps: readonly string[];
	readonly deliverables: readonly string[];
	readonly successCriteria: readonly string[];
	readonly suggestions: readonly string[];
	readonly contingencies: readonly WorkContingency[];
}
```

`WorkDraftNode` 必须包含 `detail`，`WorkNode` 使用可选 `detail` 兼容旧数据。草稿校验要求所有数组至少包含一项，风险、触发条件和兜底动作均不能为空。

数据库升级到第三版，在 `work_nodes` 增加可空的 `detail_json` 字段。新计划保存结构化详情；读取旧记录时字段为空，不阻断加载。

`WorkDecision` 增加：

```ts
readonly scheduledStart: string;
readonly scheduledEnd: string;
```

`latestStart` 继续表示风险边界，`scheduledStart` 和 `scheduledEnd` 表示用户真正应该执行的时间段，界面不再把最晚开始时间伪装成已安排时间。

## 智能理解与建议生成

工作理解器的结构化输出同步增加任务详情。提示规则要求：

- 步骤必须是能直接执行的动作，不能重复标题。
- 交付物必须具体，例如“活动初稿文档”“数据回收表”“演示文稿文字稿”。
- 完成标准必须可检查，例如“包含目标、流程、预算和三个备选场地”。
- 建议必须结合任务类型、依赖和截止时间。
- 风险必须写明何时算触发，兜底动作必须不依赖原阻塞方才能继续推进。
- 演示文稿类工作默认采用“文字叙事—数据占位—初稿—预审—终稿”顺序。
- 协作类工作要求明确反馈截止时间、二次跟进时间和备选联系人或替代信息源。
- 方案类工作要求先完成最小可审版本，再预留被驳回后的修改窗口。

重新安排时，现有任务详情一并传给理解器，仍保留的节点不得丢失已有有效建议。手动待办使用本地基础详情，不为一次简单添加额外调用模型。

## 实际时间排期与每日留白

现有倒排逻辑继续计算依赖链和最晚开始时间，随后增加一次确定性正向排期：

1. 从当前真实时间开始，向上取整到十五分钟；若当前为周末或工作时段外，推进到下一个工作日开始时间。
2. 按依赖拓扑、最晚开始时间和风险优先级排列未完成节点，依赖任务先于下游任务。
3. 每个任务使用“预计工时加个人安全缓冲”占用时间，并向上取整为十五分钟时间块；外部等待使用自然时间推进下游任务，不占用用户工作容量。
4. 每日最多使用 `dailyCapacityMinutes`，达到容量后自动推进到下一个工作日。工作日总时长与每日容量的差额明确标记为“已为临时事项保留”。
5. 不把任何工作安排到周六、周日或工作结束时间之后。
6. 正向安排晚于 `latestStart` 时，保留最早可执行时段，同时将风险升级并在详情卡显示“缩小范围、先交最小版本、改用占位数据或升级沟通”等对应兜底。
7. 零工时的手动待办保留为时间点，不占用容量。

第一版沿用现有工作习惯参数，不额外增加午休、会议或私人日历配置。当前默认工作时段为九点至十八点、每日容量七小时，因此每天至少保留两小时；以后只有用户明确需要接入私人日历时再扩展忙闲数据。

## 日历与详情交互

日历中的每个任务从静态块改为可聚焦按钮，保持原颜色和紧凑布局。卡片表面显示：

- 实际开始—结束时间；
- 任务标题；
- 负责人和状态；
- 高风险任务的风险标识。

每个工作日底部显示“已安排”和“已保留”的分钟数，周末继续保持无工作安排。

点击任务后打开原生详情对话框，不改变七列日历宽度。详情卡包含：

1. 实际时段、预计工时、最晚开始时间和负责人；
2. 任务目的；
3. 执行步骤；
4. 交付物与完成标准；
5. 助理建议；
6. 风险触发条件和兜底动作。

对话框支持键盘聚焦、退出键和明确的关闭按钮。所有模型内容继续使用纯文本节点渲染，禁止作为网页标记插入。

## 兼容与错误处理

- 数据库迁移只增加可空字段，旧项目无损升级。
- 旧节点详情由视图模型根据标题、工时、等待和排期原因生成基础版本。
- 模型返回缺失详情或空兜底时整份草稿判定无效，沿用现有一次重试机制。
- 任务不能在截止前完整排入时不隐藏冲突，详情卡明确显示风险和兜底。
- 无效时区或时间继续使用现有校验和错误结果，不在界面静默修正。

## 测试与验收

### 自动测试

1. 草稿校验拒绝缺少步骤、交付物、完成标准、建议或兜底的节点。
2. 工作理解器的真实结构化边界能接收并返回完整详情。
3. 数据库第三版迁移兼容旧库，详情保存和读取保持一致。
4. 正向排期跳过周末、遵守每日容量、保留工作时间并满足依赖顺序。
5. 日历视图返回实际开始—结束时间和每日留白。
6. 桌面界面测试验证每个任务可点击、详情字段可见、键盘可关闭且旧节点可展开。

### 验收标准

- 用户输入包含活动、演示文稿和跨人协作的复合需求后，日历展示周一至周五的实际时间段，不在周末安排工作。
- 每日显示可见留白，不把工作日填满。
- 任意任务点击后立即显示完整助理卡片，没有二次等待。
- 演示文稿任务包含先文稿后制作、数据占位、预审和打磨建议。
- 协作方不回复、老板未审核或数据缺失等情况均有具体触发条件与替代动作。
- 旧计划、手动待办、执行审批和成果验收流程继续正常工作。
